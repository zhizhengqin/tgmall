## 一、MoSCoW 分类说明

| 分类 | 含义 | 决策原则 | 占比目标 |
|------|------|----------|----------|
| **M · Must Have** | 没有它，MVP 无法上线。是产品的"心跳"。 | 不交付=项目失败。资源优先保障。 | ≤ 60% |
| **S · Should Have** | 重要但有替代方案。没有会很痛，但可以上线。 | 尽力交付。如时间不够，可延到下个版本。 | ~20% |
| **C · Could Have** | 锦上添花。做了更好，不做也不影响核心体验。 | 资源充裕时才做。不占用 M/S 的资源。 | ~15% |
| **W · Won't Have** | 明确不做（本期）。放入后续版本或永久不做。 | 坚决说不。防止需求蔓延。 | ~10% |

> ⚠️ **经验法则**：如果 Must Have 超过 60%，说明 MVP 范围太大，需要砍。  
> 参考：本矩阵 MVP Must Have **58 项 / 79 项 = 73%**（偏高，原因是平台型产品两端都有刚性需求。建议上线决策时严格把关——M 类中如果有替代方案，可降级为 S。）

## 三、MVP 必须交付详解（Must Have）

> 共 **58 项**，总估值 **238 点**。这些是产品的"心跳"——缺任何一个都无法上线。

### 3.1 为什么这些是 Must Have？

```
消费者端核心路径（不可中断）：
登录 → 浏览商品 → 查看详情 → 加入购物车 → 结算 → 支付 → 查看订单 → 收到通知
  ✅       ✅          ✅          ✅        ✅      ✅        ✅         ✅

商家端核心路径（不可中断）：
入驻 → 审核通过 → 登录后台 → 上架商品 → 收到新订单通知 → 处理订单 → 发货
  ✅       ✅         ✅         ✅           ✅             ✅        ✅

平台端核心路径（不可中断）：
审核商家 → 查看平台数据 → 系统配置
   ✅           ✅(基础)       ✅(基础)

基础设施（不可缺失）：
CI/CD + 数据库 + 缓存 + 存储 + 安全 + 三语 + 双币种
  ✅      ✅      ✅      ✅      ✅      ✅      ✅
```

### 3.2 Must Have 风险分布

| 风险等级 | 数量 | 典型项 | 应对 |
|----------|------|--------|------|
| 🔴 高风险 | 3 | KHQR 支付、ABA Pay 支付、创建订单（事务+并发） | Sprint 3 提前技术预研；准备 Fallback（COD 过渡） |
| 🟡 中风险 | 8 | 购物车、结算页、i18n 框架、Bot 框架、CI/CD、弱网优化 | Sprint 初期搭建，留足 Buffer |
| 🟢 低风险 | 47 | 列表页、详情页、地址管理、状态切换、备份等 | 标准开发节奏即可 |

### 3.3 Must Have 如果不做会怎样？

| 缺失项 | 最严重后果 |
|--------|-----------|
| 不接 KHQR 支付 | 47% 消费者无法支付，COD 仅覆盖 26.5%，ABA Pay 无法覆盖所有银行用户 |
| 不做高棉语 | 放弃 70% 本地市场，相当于放弃了最大的目标用户群 |
| 不做弱网优化 | 柬埔寨大量 3G 用户打不开 Mini App，第一天就流失 |
| 不做 Bot 通知 | 商家不知道有新订单，发货延迟 → 差评 → 流失 |
| 不做库存预占 | 超卖 → 消费者付了钱买不到 → 信任崩溃 |
| 不做 initData 校验 | 可以伪造任何人的身份下单 → 安全事故 |

## 九、需求裁剪决策树

当 Sprint 时间不够时，用下面的决策树快速判断该砍什么：

```
需求能砍吗？
│
├─ 不交付这个需求，MVP 还能不能跑通"浏览→加购→下单→支付→通知"闭环？
│  ├─ 不能 → Must Have，死也要做
│  └─ 能 → 继续往下问
│
├─ 这个需求有没有可用的替代方案？
│  ├─ 有替代方案（如手动替代自动、SQL 替代图表）→ Should Have，可降级
│  └─ 没有替代方案 → Must Have
│
├─ 这个需求用户感知强吗？
│  ├─ 强（如骨架屏→用户觉得快）→ Should Have
│  └─ 弱（如操作日志→后台功能）→ Could Have
│
├─ 这个需求如果现在不做，下周/下月做成本会翻倍吗？
│  ├─ 会（如 i18n 框架、数据库设计）→ Must Have（技术债预防）
│  └─ 不会 → Could Have / Won't Have
│
└─ 做出决策：M 保 / S 压 / C 砍 / W 弃
```

### 九.1 典型裁剪场景

**场景 1：Sprint 2 延期 1 周**

```
砍掉顺序：
1. 骨架屏（F-C39）→ Spinner 替代 → 省 2 点
2. 个人中心（F-C28）→ 底部占位页 → 省 3 点
3. 优惠券系统（F-C24/F-C25/F-C27）→ 第二期做 → 省 8 点
   ⚠️ 保留结算页优惠券选择的位置（UI 占位），后端不做
4. 如果还不够 → 搜索历史（F-C45）→ 砍 → 省 2 点

最多可省：15 点 ≈ 2-3 天
```

**场景 2：Sprint 4 延期 1 周（最关键的决策）**

```
砍掉顺序：
1. 商家数据看板（F-M14/F-M15）→ 第二期 → 省 11 点
2. 平台数据大屏（F-A04~F-A07）→ SQL 替代 → 省 19 点（最大块）
   ⚠️ 保留核心指标卡片（1 张基础表），砍掉趋势图和排行榜
3. 平台品类/佣金/Banner 配置（F-A08~F-A11）→ 数据库操作 → 省 11 点
4. 商家店铺信息编辑（F-M13）→ 联系运营 → 省 3 点

最极端可省：44 点 ≈ 1 周工作量
但砍完后：种子商家后台只有"商品管理+订单处理"两个核心功能。
建议：至少保留 F-A08（品类管理）+ F-A10（Banner），运营也需要基本的配置能力。
```

**场景 3：支付对接遇到技术障碍（KHQR API 不可用）**

```
Fallback 方案（按优先级）：
1. COD 先行 → 上线当天只支持 COD（26.5% 消费者可接受）
2. 手动确认支付 → 用户转账到平台银行账户 → 运营在后台手动标记"已付款"
3. ABA Pay 优先对接 → 如果 Bakong 卡住，先做 ABA Pay（市场份额最大银行）
4. 给种子商家+种子消费者提供"先货后款"→ 信任期内过渡
```
