## 第一部分：软件工程是什么？——用开店来理解

### 1.1 软件工程 = 科学的"开店"流程

想象你要在柬埔寨金边开一家跨境电商体验店：

| 开实体店      | 做软件      | 通俗解释                   |
| ---------- | -------- | ---------------------- |
| **立项**     | **立项**   | 老板拍板："我们要开店/做平台"    |
| **市场调研**   | **需求分析** | 这条街卖什么好？谁是我们的客人？     |
| **店铺设计**   | **系统设计** | 设计师画图纸：门面、货架、收银台布局  |
| **装修施工**   | **编码开发** | 工人按图纸砌砖、布线、装收银系统    |
| **试营业检查**  | **测试验证** | 检查收银机好不好用、货架稳不稳      |
| **正式开业**   | **部署上线** | 放鞭炮开业，迎接第一批顾客        |
| **日常经营**   | **运维迭代** | 补货、换灯泡、根据顾客反馈调整陈列    |

**软件工程的本质**：不是一上来就敲代码，而是先想清楚"开什么样的店、卖给谁、怎么卖"，再一步步科学地推进。跳过前面任何一步，后面都会返工（就像没设计好收银台位置，装修完才发现堵住通道）。

### 1.2 为什么必须按流程走？——柬埔寨项目的特殊考量

在柬埔寨做 Telegram 电商平台，比国内更容不得返工：

1. **本地技术人才稀缺**：找一个熟悉 Telegram Mini App 开发的工程师比国内难 3 倍，返工成本极高
2. **网络基础设施不稳定**：没提前设计好弱网降级方案，顾客扫码后页面半天打不开
3. **支付生态复杂**：KHQR/ABA Pay/Wing Pay 多渠道对接，没设计好架构后面改不动
4. **多语言环境**：高棉语+英语+中文，UI 没预留扩展，后期改起来伤筋动骨
5. **Telegram 生态特殊性**：Mini App 有独特限制（如支付必须由 Telegram 原生处理），前期没调研透，开发到一半推翻重来

**结论**：前期多花 1 周做设计，后期省掉 2 个月返工。

## 第二部分：软件工程六大阶段详解（科普版）

### 阶段一：需求分析 —— "这家店卖什么？谁来买？"

**生活化理解**：
你请设计师装修店铺，第一步不是买材料，而是坐下来聊：这条街的人流是谁？年轻人还是中老年人？卖什么品类？要不要配沙发？这些"需求"决定了后面的一切。

**软件工程定义**：
把"老板的想法"和"用户的需要"翻译成开发团队能看懂的、不模糊的语言。

**关键问题清单**：

- 谁用？（柬埔寨年轻消费者、在柬华人、本地消费者）
- 用什么设备？（智能手机为主，柬埔寨人均多部低价安卓机）
- 核心场景是什么？（浏览商品 → 加购物车 → 下单 → 扫码支付 → 查看物流）
- 必须有什么？（没有就不能上线）
- 最好有什么？（有了更好，没有也能先跑）
- 绝对不能有什么？（比如绝对不能碰用户资金，必须走银行/KHQR 通道）

**常见陷阱**：

- ❌ "做一个像 Shopee 那样的系统" → 太模糊，无法执行
- ✅ "消费者在 Telegram Mini App 中浏览商品后，3 秒内加载商品详情页，点击购买后跳转 Telegram 原生支付完成 KHQR 扫码" → 可测量、可验证

---

### 阶段二：系统设计 —— "画图纸，定结构"

**生活化理解**：
需求聊完了，设计师开始画三件套图纸：

- **建筑结构图**：承重墙在哪、房间怎么布局 → 软件里的"系统架构图"
- **水电施工图**：水管怎么走、电线怎么布 → 软件里的"数据库设计"和"接口设计"
- **装修设计图**：墙面颜色、货架材质 → 软件里的"UI 原型图"

**软件工程定义**：
把需求转化为技术实现方案，回答"用什么技术、怎么组织代码、数据怎么存、各个模块怎么通信"。

**关键产出**：

- 系统架构图（店铺有几层、什么结构）
- 数据库设计（仓库怎么分区、货物怎么编号）
- API 接口文档（收银台和仓库之间的门开在哪个位置）
- UI/UX 原型图（每个页面的草稿图）

---

### 阶段三：编码开发 —— "装修工人进场"

**生活化理解**：
图纸定好了，工人开始砌墙、铺管、装收银系统。这时候老板不需要亲自搬砖，但需要：

- 每天看看进度（日报）
- 检查材料对不对（代码审查）
- 确保没偷工减料（质量把控）

**软件工程定义**：
程序员根据设计文档写代码，把图纸变成真店铺。

**你的角色**：

- 不是写代码，而是**管理进度和质量**
- 用"每日站会"（15 分钟）了解：昨天做了什么、今天做什么、遇到什么障碍
- 要求开发团队每周给你看"可运行的半成品"（Demo），而不是等到最后才看

---

### 阶段四：测试验证 —— "试营业检查"

**生活化理解**：
店铺装修好了，不能马上正式开业。要先检查：

- 试试收银机好不好用（功能测试）
- 100 人同时进店会不会挤爆（性能测试）
- 请几个朋友来模拟购物，看哪里不方便（用户验收测试/UAT）

**软件定义**：
在正式给顾客用之前，尽可能找出 Bug（缺陷），确保系统稳定、安全、好用。

**测试类型**：

- **功能测试**：扫码能不能付款？优惠券能不能用？
- **性能测试**：100 个人同时下单，系统会不会卡死？
- **安全测试**：黑客能不能盗刷？
- **兼容性测试**：在柬埔寨常见的低端安卓机上能不能用？

---

### 阶段五：部署上线 —— "正式开业"

**生活化理解**：
试营业通过了，放鞭炮正式开业。但开业不是开门就完事，还要：

- 开通水电煤气（服务器配置、域名绑定）
- 给店员一本《操作手册》（用户手册）
- 留一个维修电话（运维支持）

**软件定义**：
把开发好的系统安装到生产环境（真正的服务器上），让真实用户可以访问。

**关键动作**：

- 准备生产环境服务器（AWS 新加坡区域，满足柬埔寨数据合规）
- 配置域名和 SSL 证书（HTTPS 加密，让用户支付时数据安全）
- 数据迁移（测试数据清空，准备迎接真实用户/消费者）
- 上线 checklist（逐项确认，防止遗漏）

---

### 阶段六：运维与迭代 —— "日常经营和重新装修"

**生活化理解**：
开业之后：

- 灯泡坏了要换（修 Bug）
- 想加个货架（新功能开发）
- 水电费要交（服务器续费、域名续费）
- 经营半年后，可能想重新装修门面（大版本升级）

**软件定义**：
系统上线后的日常维护、问题修复、功能优化和版本升级。

**你的日常工作**：

- 看系统监控大屏（今天有多少订单？系统卡不卡？）
- 收集用户反馈（哪个功能不会用？哪里经常出错？）
- 排优先级（先修致命 Bug，再做好用的功能）

## 第三部分：Telegram Mini App 电商平台项目全流程实战地图

现在，我们把上面的六大阶段，**具体映射到你的 Telegram Mini App 电商项目上**。每个阶段告诉你：做什么、产出什么、怎么指导开发、小白怎么参与。

> **项目范围说明**：根据商业计划书，分三期推进。本期（MVP）聚焦核心交易闭环，先让"买卖跑起来"。

---

### 🔷 阶段一：需求分析（第 1-2 周）

#### 1.1 本阶段目标

把商业计划书的"三大商业模式"和"三大阶段产品路线"翻译成程序员能执行的"功能清单"。

#### 1.2 核心工作

**A. 梳理用户角色（谁用系统）**

你的系统有 4 类用户，像一家店有 4 种角色：

| 角色       | 身份           | 核心诉求             | 使用频率       |
| -------- | ------------ | ---------------- | ---------- |
| **消费者**  | 柬埔寨本地年轻人、华人、游客 | 看商品、下单、扫码支付、查物流 | 高频（想买就用）   |
| **平台管理员** | 运营/商品/订单管理人员 | 上架商品、处理订单、看销售数据 | 中频（每天管理后台） |
| **平台运营** | 你和你的团队       | 商品管理、看大盘数据、处理投诉  | 中低频        |
| **配送员**  | 物流公司（第三方）    | 接单、更新配送状态        | 中频         |

**B. 梳理功能模块（MVP 必做 vs 后期再做）**

用"四象限法"分类：

```
紧急且重要（MVP 必做）          重要但不紧急（第二期）
├─ 商品浏览与搜索                 ├─ 用户评价与评分系统
├─ 购物车与下单                  ├─ AI 智能推荐
├─ KHQR/ABA Pay/Wing Pay 支付   ├─ 直播购物
├─ 订单追踪                     ├─ 社群团购
├─ 平台商品上架              ├─ 跨境购
├─ 管理员订单管理后台         ├─ 供应链金融
├─ Telegram Bot 订单通知       ├─ 完整广告管理系统
├─ 基础优惠券系统                 
├─ 用户注册/登录（Telegram 原生）

紧急不重要（可外包/用现成）       不紧急不重要（暂不做）
├─ 高棉语翻译（雇本地翻译）        ├─ 区块链积分
├─ 短信网关对接（用 Twilio）      ├─ AR/VR 购物
├─ 服务器部署（用 AWS 托管）      ├─ 复杂的数据分析 AI 预测
└─ 第三方物流对接（用现成 API）
```

**C. 编写用户故事（User Stories）**

用户故事是需求分析的核心武器，格式固定为：

> **作为** [某种用户]，**我想** [做某事]，**以便** [获得某种价值]

示例（你的项目）：

```
US-001：浏览商品
作为 柬埔寨消费者
我想 在 Telegram Mini App 里按品类浏览商品，看到高棉语的商品名称和价格
以便 快速找到我想买的东西

US-002：加入购物车
作为 柬埔寨消费者
我想 把喜欢的商品加入购物车，支持多规格选择（如颜色、尺码）
以便 一次性购买多件商品

US-003：下单支付
作为 柬埔寨消费者
我想 点击"立即购买"后，选择 KHQR 扫码支付或 ABA Pay
以便 用我熟悉的支付方式完成付款

US-004：平台上架商品
作为 平台管理员
我想 在管理员后台上传商品图片、填写价格（支持 USD 和 KHR 双币种）、设置库存
以便 消费者能在 Mini App 中看到平台商品

US-005：订单通知
作为 平台管理员
我想 消费者下单后，Telegram Bot 立即推送通知给我
以便 我第一时间处理订单、安排发货

US-006：平台数据看板
作为 平台运营人员
我想 每天早上一张图表显示：昨日订单量、GMV、新增用户数、支付成功率
以便 我快速判断业务健康度
```

**D. 定义验收标准（Definition of Done）**

每个用户故事必须满足什么条件才算"做完了"？例如：

```
US-003 验收标准：
✅ 消费者点击购买后，Telegram 原生支付弹窗在 2 秒内出现
✅ 支持 KHQR 扫码支付，支付完成后订单状态自动变为"已付款"
✅ 支持 ABA Pay 跳转，支付回调后订单状态同步更新
✅ 支付失败时，页面显示高棉语/英语/中文的错误提示
✅ 在柬埔寨 3G 网络环境下测试通过（页面加载不超过 5 秒）
✅ 高棉语、英语、中文三种语言切换正常
✅ 价格同时显示 USD 和 KHR（按当日汇率换算）
```

#### 1.3 阶段产出物清单

| 产出物              | 是什么                                                                                    | 为什么重要                                   | 怎么指导开发                                     |
| ---------------- | -------------------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------ |
| **《产品需求文档（PRD）》**  | 一份 20-40 页的 Word/Markdown 文档，包含：项目背景、用户角色、功能清单、用户故事、验收标准、非功能需求（性能/安全） | 这是开发团队的"圣经"。没有它，程序员会凭想象开发，做出来不是你想要的 | 开发团队每写一行代码前，先问"这行代码对应 PRD 里的哪个需求？"    |
| **《用户故事清单（Backlog）》** | 把所有功能拆成一条条用户故事，用 Excel 或项目管理工具（如 Trello、Notion）管理                              | 把大目标拆成可执行的小任务，方便排期和跟踪                  | 开发团队按优先级一条条"认领"，做完一条勾掉一条               |
| **《需求优先级矩阵》**      | 用 MoSCoW 法则分类：Must have（必须有）、Should have（应该有）、Could have（可以有）、Won't have（暂不做）      | 防止"需求蔓延"——开发过程中不断加新需求导致项目延期          | 开发团队先全力做 Must have，有时间再做 Should have    |
| **《原型草图（低保真）》**    | 手绘或工具画的页面草稿，不讲究美观，只讲究布局和流程                                                  | 让开发团队直观理解"页面长什么样、点哪个按钮跳到哪"          | 程序员对着草图写前端页面，设计师后期再美化                    |

#### 1.4 小白怎么参与？

- ✅ **你必须亲自做**：用户故事编写（因为你最懂柬埔寨消费者的需求）、验收标准定义（因为你最清楚什么算"能用"）
- ✅ **你可以主导**：PRD 文档的框架搭建、需求优先级排序
- ❌ **建议交给设计师/产品经理**：低保真原型图（如果你完全没用过 Figma，可以手绘拍照）

### 🔷 阶段二：系统设计（第 3-4 周）

#### 2.1 本阶段目标

把 PRD 里的文字需求，变成技术实现方案。回答三个核心问题：

1. **系统怎么分层？**（Mini App 前端、后端、数据库怎么配合）
2. **数据怎么存？**（商品、订单、用户存在哪里，怎么关联）
3. **模块怎么通信？**（消费者下单后，信息怎么传到平台管理员 Telegram）

**技术选型理由（给小白看的解释）**：

| 技术              | 作用       | 为什么选它                                   | 小白理解           |
| --------------- | -------- | --------------------------------------- | -------------- |
| **Vue.js / React** | Mini App 前端 | 适合构建单页应用，Telegram Mini App 官方推荐；组件化开发快 | 店铺的门面装修，顾客第一眼看到的 |
| **Node.js / Python** | 后端框架    | JavaScript 全栈统一或 Python 开发快；社区庞大，招聘相对容易   | 店铺的后勤管理系统       |
| **PostgreSQL**   | 主数据库    | 开源免费、支持高棉语 Unicode、关系型数据适合电商订单/商品    | 仓库的货架和库存台账      |
| **Redis**        | 缓存      | 存临时数据（如购物车、登录状态），读写极快               | 收银台旁边的临时储物柜     |
| **Telegram Mini App** | 消费者端  | 无需下载 App，Telegram 内即点即用；550 万用户基础       | 开在 Telegram 里的店铺分店 |
| **Telegram Bot** | 消息推送    | 订单通知、客服消息；开发简单；免费                  | 店铺的对讲机和广播系统     |
| **AWS 新加坡**     | 云服务器    | 柬埔寨认可的数据存储地；延迟低；稳定                 | 店铺建在靠谱的商业区      |

**B. 数据库设计（ER 图）**

**C. API 接口设计**

API 就像模块之间的"门"和"窗户"——定义了不同模块之间怎么传递信息。用 RESTful 风格设计：

```
【用户模块】
POST   /api/v1/users/auth/telegram    → Telegram 一键登录
GET    /api/v1/users/me               → 获取当前用户信息
PUT    /api/v1/users/me/profile       → 更新用户资料

【商品模块】
GET    /api/v1/products               → 商品列表（支持筛选/分页）
GET    /api/v1/products/{id}          → 商品详情
GET    /api/v1/products/categories    → 品类列表

【购物车模块】
POST   /api/v1/cart/items             → 添加商品到购物车
GET    /api/v1/cart                   → 查看购物车
PUT    /api/v1/cart/items/{id}        → 修改购物车商品数量
DELETE /api/v1/cart/items/{id}        → 删除购物车商品

【订单模块】
POST   /api/v1/orders                 → 创建订单
GET    /api/v1/orders/{id}            → 订单详情
GET    /api/v1/orders                 → 我的订单列表
POST   /api/v1/orders/{id}/cancel     → 取消订单

【支付模块】
POST   /api/v1/payments/khqr          → 生成 KHQR 支付码
POST   /api/v1/payments/aba_pay       → 发起 ABA Pay 支付
POST   /api/v1/payments/callback      → 支付回调通知

【平台管理模块】
POST   /api/v1/admin/products          → 平台上架商品
GET    /api/v1/admin/dashboard         → 管理员数据看板
GET    /api/v1/admin/orders            → 管理员订单列表
POST   /api/v1/admin/orders/{id}/ship  → 管理员发货

【消息模块】
POST   /api/v1/messages/telegram      → 发送 Telegram 通知
```

**D. UI/UX 设计（高保真原型）**

在低保真草图基础上，设计师用 Figma 等工具制作高保真原型：

- **消费者 Mini App**：首页 → 分类 → 商品详情 → 购物车 → 订单确认 → Telegram 原生支付 → 订单中心
- **管理员后台**：登录页 → 数据看板 → 商品管理 → 订单管理 → 优惠券创建 → 数据统计
- **平台后台**：大盘数据 → 系统配置 → 用户管理

**柬埔寨本地化设计要点**：

- 高棉语文字较长，按钮宽度要比中文多 30%
- 柬埔寨用户习惯大字号（很多中老年人用手机）
- 主色调建议用金色+红色（柬埔寨文化中的吉祥色）
- 必须支持 KHR 和 USD 双币种同时显示
- 商品图片要大而清晰（柬埔寨用户喜欢"看图说话"）
- 加载动画要明显（弱网环境下让用户知道"正在努力加载"）

### 4.4 关键决策点：什么时候该坚持，什么时候该妥协？

```
必须坚持（红线）：
✅ 数据安全（用户手机号、支付信息必须加密，PCI DSS 合规）
✅ 高棉语支持（没有高棉语等于放弃 70%本地市场）
✅ 双币种显示（柬埔寨法律要求，所有价格必须同时显示 USD 和 KHR）
✅ 支付安全（绝对不能碰用户资金，必须走 KHQR/银行官方通道）
✅ Mini App 加载速度（3 秒内必须看到首页，否则用户直接关掉）

可以适当妥协（黄线）：
🟡 UI 美观度（先能用，再好看）
🟡 功能完整性（第一期没有"AI 推荐"也能跑）
🟡 性能极致（先支持 100 并发，再优化到 1000 并发）
🟡 物流系统（第一期先手动录入物流单号，第二期再自动对接）

建议果断砍掉（黑线）：
❌ 第一期做直播购物（技术复杂度高，需 3-6 个月，等不起）
❌ 第一期做 AI 智能推荐（需要大量用户数据积累，没数据白做）
❌ 第一期做自有物流体系（自建物流需要数百万美元投入，先用第三方）
❌ 第一期做复杂广告系统（先靠 Telegram Channel 免费推广）
```

### 5.2 非技术出身的你，最容易犯的 5 个错误

1. **急着写代码，懒得写文档** → 结果：开发 2 个月后发现方向错了，推倒重来
   - **对策**：前两周坚决不写代码，只写 PRD 和设计文档

2. **追求完美，想一次性做全所有功能** → 结果：6 个月过去了还没上线，市场窗口关闭
   - **对策**：MVP 思维，先上线"能买东西"的最小版本

3. **不懂技术，所以完全不管技术** → 结果：团队用老旧技术栈，后期维护成本极高
   - **对策**：要求技术负责人给你讲选型理由，你不懂就问，直到听懂

4. **只关注功能，不关注 Telegram Mini App 的特殊性** → 结果：开发出来在 Telegram 里打不开，或支付不符合规范
   - **对策**：第 1 周就让技术负责人读完 [Telegram Mini App 官方文档](https://core.telegram.org/bots/webapps)，确认没有技术盲区

5. **忽视柬埔寨本地特殊性** → 结果：系统在国内跑得好，到柬埔寨各种报错
   - **对策**：从第一天开始，所有测试都用柬埔寨真实手机号、真实网络环境、真实 KHQR 支付

### 5.3 Telegram Mini App 开发特别提醒

Telegram Mini App 不是普通网页，有独特的限制和最佳实践，必须提前了解：

```
⚠️ 必须使用 Telegram 原生支付：Mini App 内不能自定义支付页面，
   必须调用 Telegram.Payments 原生接口，否则会被封

⚠️ initData 验证：每个 Mini App 启动时都会携带 initData，
   后端必须校验其真实性，防止伪造请求

⚠️ 包体积限制：Mini App 前端包不能太大（建议 < 2MB），
   否则在柬埔寨弱网环境下打不开

⚠️ 没有本地存储：Mini App 的 localStorage 可能不持久，
   购物车等数据需要后端同步或加密存储

⚠️ 返回按钮处理：Telegram 客户端有物理返回按钮，
   需要在代码中正确响应，否则用户体验很差

⚠️ 主题适配：Mini App 需要适配 Telegram 的亮色/暗色主题，
   使用 Telegram 提供的 themeParams 动态调整颜色
```

## 结语：你不是一个人在战斗

作为非技术出身的技术负责人，你的核心优势不是写代码，而是：

1. **最懂业务**：你知道柬埔寨消费者真正需要什么、平台运营真正在乎什么
2. **最懂用户**：你知道高棉语消费者的购物习惯、Telegram 使用方式
