### EPIC-01：用户与认证

#### S1-04：Telegram 一键登录 — 前端

**估点**：5  
**优先级**：P0 · Must Have  
**角色**：前端开发

---

**用户故事**

> **作为** 柬埔寨消费者
> **我想** 打开 Mini App 时自动用我的 Telegram 账号登录，无需填写任何表单  
> **以便** 最快速度开始浏览商品

---

**验收标准**

- [ ] **AC1：自动获取** — Mini App 打开时，调用 Telegram WebApp SDK 的 `WebApp.initData` 获取用户标识
- [ ] **AC2：首次授权** — 首次打开 Mini App 时，Telegram 原生弹出授权请求（"XXX 将知道你是谁"），点击"同意"后进入
- [ ] **AC3：加载状态** — 登录过程中显示 Loading 动画（非白屏），超过 5 秒显示重试按钮
- [ ] **AC4：Token 存储** — 登录成功后 Token 存储在前端（localStorage 优先，不支持则内存存储），后续请求自动附带
- [ ] **AC5：Token 过期** — Token 过期（24 小时）后自动重新获取 initData 刷新 Token，用户无感知
- [ ] **AC6：退出登录** — 个人中心提供"退出登录"按钮，清除本地 Token 和缓存数据（购物车除外）
- [ ] **AC7：暗色主题适配** — 登录过程 UI 适配 Telegram 的亮色/暗色主题（使用 `WebApp.themeParams`）

#### S1-05：Telegram 一键登录 — 后端

**估点**：5  
**优先级**：P0 · Must Have  
**角色**：后端开发

---

**用户故事**

> **作为** 后端系统
> **我想** 验证来自 Telegram Mini App 的 initData 真实性，并创建或匹配用户账号  
> **以便** 确保请求来自真实的 Telegram 用户，防止伪造请求

---

**验收标准**

- [ ] **AC1：签名验证** — 使用 Bot Token 通过 HMAC-SHA256 验证 `initData` 的 `hash` 字段，签名不匹配则返回 401
- [ ] **AC2：时效检查** — 检查 `initData` 中的 `auth_date`，超过 24 小时则拒绝（防重放攻击）
- [ ] **AC3：自动创建** — 首次登录用户自动创建账号：`telegram_id`、`first_name`、`last_name`、`username`、`language_code`
- [ ] **AC4：老用户匹配** — 已存在的 `telegram_id` 直接匹配，返回 JWT Token
- [ ] **AC5：JWT 签发** — Token 包含：`user_id`、`telegram_id`、签发时间、过期时间（24h）
- [ ] **AC6：API 鉴权中间件** — 所有 `/api/v1/*` 接口（除白名单外）校验 JWT，无效返回 401
- [ ] **AC7：默认语言推断** — 根据 Telegram 返回的 `language_code` 设置用户偏好语言（`km`/`en`/`zh`），存入库
- [ ] **AC8：请求日志** — 登录请求记录结构化日志（`user_id`、IP、时间、结果），方便排查异常

#### S1-07：商品列表 API

**估点**：5  
**优先级**：P0 · Must Have  
**角色**：后端开发

---

**用户故事**

> **作为** Mini App 前端
> **我想** 调用商品列表 API 获取商品数据，支持按品类、关键词、排序方式筛选  
> **以便** 消费者能看到商品列表

---

**验收标准**

- [ ] **AC1：接口定义** — `GET /api/v1/products`
- [ ] **AC2：分页** — 支持 `page` 和 `limit` 参数（默认 page=1, limit=20），返回 `total`、`total_pages`、`has_next`
- [ ] **AC3：品类筛选** — 支持 `?category=fashion` 按品类过滤（fashion/beauty/electronics/home）
- [ ] **AC4：关键词搜索** — 支持 `?q=ខោអាវ`（高棉语）、`?q=dress`（英语）、`?q=衣服`（中文）多语言搜索，使用 PostgreSQL `ILIKE` 或全文搜索
- [ ] **AC5：排序** — 支持 `?sort=newest`（最新）、`?sort=price_asc`（价格低→高）、`?sort=price_desc`（价格高→低）、`?sort=popular`（销量）
- [ ] **AC6：响应格式** — 每条商品返回：`id`、`name`（根据请求 `Accept-Language` 头返回对应语言）、`thumbnail`（第一张图片）、`price_usd`、`price_khr`、`category`
- [ ] **AC7：性能** — P95 响应时间 < 200ms（无缓存），< 50ms（Redis 缓存命中），数据库查询加索引（`category`、`status`、`created_at`）
- [ ] **AC8：仅返回在售** — 默认只返回 `status=active` 且 `stock > 0` 的商品
- [ ] **AC9：限流** — 此接口 Rate Limit 60 req/min（普通用户级别）

**用户故事**

## 九、Definition of Done（完成定义）

每条 User Story 必须满足以下所有条件才算 **Done**：

### 9.1 开发完成

- [ ] **代码完成** — 功能代码已实现，通过自测
- [ ] **代码审查** — 至少 1 名同级开发者 Code Review 通过
- [ ] **代码合并** — 通过 PR 合并到 `dev` 分支，无冲突
- [ ] **代码规范** — ESLint/Prettier 无警告；Commit 遵循 Conventional Commits

### 9.2 测试通过

- [ ] **验收标准** — 本 Story 所有验收标准（AC）全部通过
- [ ] **单元测试** — 新增代码单元测试覆盖（核心逻辑覆盖率 ≥ 80%）
- [ ] **集成测试** — 涉及 API 变更的，集成测试通过
- [ ] **真机验证** — Mini App 前端变更在 ≥ 1 台 Android 真机上验证通过
- [ ] **三语验证** — 面向用户的文案三语切换验证通过（如适用）
- [ ] **无回归 Bug** — 确认未引入新的 P0/P1 Bug

### 9.3 文档与部署

- [ ] **API 文档** — 如有 API 变更，Swagger 文档已更新
- [ ] **Staging 部署** — 已部署到 Staging 环境并验证通过
- [ ] **Story 关闭** — 在项目管理工具中标记为 Done

## 十、Story 编写规范说明

### 10.1 估点参考基准

| 点数 | 含义 | 示例 |
|------|------|------|
| **1** | 微小改动，半天内 | 修改一个文案、修复一个简单 Bug |
| **2** | 小任务，1 天内 | 新增一个 API 字段、调整一个页面样式 |
| **3** | 中等任务，1-2 天 | 新增一个简单页面、一个标准 CRUD API |
| **5** | 较大任务，2-4 天 | 一个完整功能模块（前后端）、带集成测试 |
| **8** | 大型任务，4-6 天 | 复杂交互页面（如购物车、结算页）、支付集成 |
| **13** | 超大任务，需拆分 | 跨 Sprint 的史诗级功能 |

### 10.2 优先级定义

| 优先级 | 含义 |
|--------|------|
| **P0 · Must Have** | 没有此功能，MVP 无法上线 |
| **P1 · Should Have** | 重要但有替代方案，没有的话体验受损但可上线 |
| **P2 · Could Have** | 锦上添花，可后延 |
| **P3 · Won't Have** | 明确不做（放入后续版本） |

### 10.3 维护规则

1. **Stories 是活的**：每个 Sprint 结束后需根据实际完成情况更新估点和状态
2. **新增 Story**：需求变更或发现遗漏时，按格式新增；需同时评估对当前 Sprint 的影响
3. **估点调整**：实际耗时与估点偏差 > 50% 的 Story，在 Sprint 回顾中讨论原因并更新估点基准
4. **Backlog Grooming**：每两周（Sprint 计划会前）花 1 小时对下个 Sprint 的 Story 进行梳理和估点确认
5. **Done 即 Done**：未通过 Definition of Done 全部检查项的 Story，不能标记为 Done
